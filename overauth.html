What your visitor's login does

  1. Your page calls OvermindAuth.signIn(user, pass).
  2. The password is hashed with SHA-256 in the browser — the plain password never touches your server.
  3. The key id, the key hash, the username, the password hash and your origin go to the overauth_verify function in your Supabase project.
  4. Overmind checks the key (active? expired? origin allowed?) then the account (exists? password matches? banned?).
  5. You get { ok: true, user: { username } } plus a session token you can re-validate later.

overAuth 1.0 documentation

    
Everything the SDK does, and the honest security notes.


    
1 · Load the SDK

    

      
      
<script src="https://v0idplayy-777.github.io/Overmind/overauth.js"></script>

    

    
No dependencies, ~13 KB gzipped, works on http and https, and in Node 18+.


    
2 · JavaScript API

    

      
CallWhat it does

      
        
init(options)Loads your key. { key, origin?, mode?, storage?, remember?, onAuthChange? } → resolves with key info and whether the SQL backend is installed.

        
signIn(user, pass)The one you want. Checks the username/password, keeps the visitor signed in, returns the result object.

        
checkCredentials(user, pass)Same check, but does not store a session — use it if you handle state yourself.

        
getSession()Restores (and in DB mode re-validates) the stored session. Resolves to a result object or null.

        
signOut()Clears the local session and revokes the token server-side.

        
currentUser()The signed-in user object, or null.

        
onAuthChange(cb)Fires on SIGNED_IN, SIGNED_OUT, SESSION_RESTORED, ERROR. Returns an unsubscribe function.

        
mount(target, opts)Renders the login card into a selector/element.

        
renderButton(target, opts)Renders a “Continue with Overmind” button that opens the card in a modal.

        
backendStatus()Resolves 'ready' or 'missing' — whether supabase/overauth.sql is installed.

      
    


    
3 · The result object

    

      
      
// success
{
  "ok": true,
  "mode": "db",                     // "db" = SQL backend, "local" = no-SQL fallback
  "user": { "username": "alice", "created_at": "2026-07-29T05:03:15" },
  "key":  { "key_id": "oak_1a2b3c4d5e6f7a8b", "name": "My blog — production" },
  "session_token": "8fQk…",         // re-validate it later with overauth_session()
  "session_expires_at": "2026-10-05T12:00:00+00:00"
}

// failure
{
  "ok": false,
  "reason": "invalid_credentials",  // machine-readable, see table below
  "message": "Incorrect username or password."  // safe to show the visitor
}

    


    

      
reasonMeaning

      
        
invalid_credentialsNo such Overmind account, or the password doesn't match.

        
account_bannedThe account is banned on Overmind.

        
invalid_keyKey malformed, tampered with, not issued by Overmind, or revoked+deleted.

        
key_revokedYou paused or deleted the key in this console.

        
key_expiredPast the expiry date you picked.

        
origin_not_allowedThe site's origin isn't on the key's allow-list.

        
invalid_sessionSession token unknown, revoked or expired.

        
missing_credentialsEmpty username or password.

        
backend_error / network_errorSupabase returned an error, or couldn't be reached.

5 · Two modes

    
    
      
  • DB mode — you ran supabase/overauth.sql. Keys are stored as hashes in
          overauth_keys, so you can pause, edit, revoke and see usage counts. Visitors get
          real session tokens you can re-validate from your own backend. This is the mode you want.
    • 
      
  • Local mode — nothing installed yet. The key is a signed, self-contained token; credentials are
          checked straight against the Overmind users table. It works instantly, but keys
          live in this browser, can't be revoked, and sessions are browser-only. Install the SQL to upgrade: the
          console re-registers your local keys server-side (same key string) the next time you sign in, so nothing
          on your site has to change.
    • 
    


    
6 · Security, honestly

    
!

      Overmind stores passwords as unsalted SHA-256. The hash is therefore password-equivalent: anyone who
      holds it can log in as that user. Always serve your site over HTTPS, never log the hash, and never put it in a
      URL. This is how the Overmind app itself already works — overAuth doesn't make it worse, but it does spread it
      to more sites, so use one key per site and revoke what you don't need.
    

    
    
      
  • Only the hash of your key is stored server-side. Losing the raw key means creating a new one.
    • 
      
  • Overmind's Supabase anon key is public (it ships inside the web app), so all real
          enforcement lives in RLS + the SECURITY DEFINER functions in
          overauth.sql. Those tables have no anon policies.
    • 
      
  • Origin checking happens in the browser, so a determined attacker can spoof the
          Origin value. Treat it as abuse prevention, not as authentication — for hard
          enforcement, call overauth_verify from your server (see the REST tab).
    • 
      
  • There is no rate limiting built in. If you expect abuse, put a cache or a limit in front of your login
          form, or add Supabase's rate-limit protection.
    • 
      
  • ⚠️ Right now the users table lets anyone with the anon key read every row,
          including password_hash. That predates overAuth, but it means all Overmind
          password hashes can be downloaded and cracked offline. See supabase/harden-users-rls.sql
          for the fix.
    • 
    


    
7 · FAQ

    

      Do my visitors need a new account?
      
No — that's the whole point. They use the username and password they already have on Overmind. Send people who don't have one to the Overmind app to register.

    

    

      Can I use it on localhost?
      
Yes. Add http://localhost:* (or the exact http://127.0.0.1:5173) to the key's allowed origins.

    

    

      One key or one per site?
      
One per site. That way you can see which site logins come from, and revoking a compromised site doesn't break the others.

    

    

      How do I keep someone logged in?
      
The SDK does it for you: it stores the session token in your site's localStorage and getSession() re-validates it (at most once every 12 hours). On your backend, call overauth_session(p_token) whenever you want to check it.

    

    

      Does it work without JavaScript on my server?
      
Yes — it's a plain HTTPS POST to Supabase. See the “REST / any language” and “Node / backend” tabs above.

    

    

      What happens if I delete a key?
      
Every login attempt with it returns invalid_key, and all sessions minted by it are revoked immediately.

    

    

      I ran the SQL but the chip still says “local mode”.
      
PostgREST caches the list of functions it exposes. Wait ~10 seconds and hit Re-check. If it's still stuck, run notify pgrst, 'reload schema'; in the SQL editor (or restart the Supabase project) and check again.

    

    

      I lost a key. Can you show it to me again?
      
Only if you're on the same browser you created it with — the console keeps a private copy there (“copyable” pill). Overmind itself stores just a SHA-256 hash, so nobody can recover it. Otherwise, create a new key and delete the old one.
